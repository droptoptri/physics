# Развёртывание и работа администратора

Для первого размещения домена REG.RU используйте [пошаговую инструкцию REG.RU](REG-RU.md). Она включает готовый Docker Compose и HTTPS. Ниже — вариант без Docker и команды администратора.

# Инструкция администратору

## Сервер

Нужны Node.js 24+, HTTPS reverse proxy и постоянный диск. Приложение хранит заявки и аккаунты в SQLite; один экземпляр Node обслуживает одну базу. Не запускайте несколько независимых почтовых worker над одной базой: доставка очереди рассчитана на один процесс. Для нескольких экземпляров понадобится отдельная очередь и блокировка задач.

```sh
npm ci
npm run build
```

Создайте закрытый `.env` на сервере на основе `.env.example`, без помещения в Git. Рекомендуемые несекретные параметры:

```dotenv
PORT=3000
NODE_ENV=production
APP_ORIGIN=https://sgt-holding.ru,https://cons.sgt-holding.ru
DATA_DIR=/srv/sgt-data
TRUST_PROXY=1
SMTP_HOST=HOST_FROM_YOUR_MAIL_PROVIDER
SMTP_PORT=465
SMTP_SECURE=true
SMTP_FROM=СГТ-КСК <partners@sgt-holding.ru>
```

`SESSION_SECRET` — случайная строка не короче 32 символов; сгенерируйте её локально на сервере (`openssl rand -hex 32`) и сохраните в закрытой конфигурации. `SMTP_USER` и `SMTP_PASS` берутся у выбранного почтового провайдера и задаются там же. Не передавайте пароли в чат и не добавляйте их в репозиторий. Адрес отправителя должен быть разрешён провайдером.

Порт 465 использует TLS сразу; 587 — STARTTLS с обязательным шифрованием (`SMTP_SECURE=false`). Проверка сертификатов остаётся включённой. Если облачная платформа поддерживает только HTTPS-прокси секретов, не используйте его placeholder как SMTP-пароль: SMTP требует действительных учётных данных в окружении production-сервера и разрешённого исходящего SMTP-соединения.

Запуск: `npm start`. Закрепите процесс через systemd или другой штатный менеджер. Production без `SESSION_SECRET` и HTTPS `APP_ORIGIN` намеренно не запускается.

## Поддомен cons.sgt-holding.ru

Это поддомен основного домена; отдельная регистрация доменного имени не нужна.

1. Создайте DNS CNAME `cons` → `sgt-holding.ru` (либо A/AAAA на тот же сервер).
2. Добавьте `cons.sgt-holding.ru` в настройки сайта/reverse proxy и сертификат TLS.
3. Передавайте исходный Host в Node; укажите оба HTTPS origin в `APP_ORIGIN`.
4. Проверьте, что открытие корня `cons.sgt-holding.ru` возвращает 302 на `/ksk`. Это уже реализовано в сервере и открывает консорциум сразу, сохраняя имя поддомена.

Аккаунты и данные общие для обоих хостов, но cookie для безопасности привязаны к конкретному хосту. Вход на одном хосте не авторизует автоматически на другом.

Пример nginx-фрагмента (в существующем HTTPS server с сертификатом для обоих имён):

```nginx
server_name sgt-holding.ru cons.sgt-holding.ru;
client_max_body_size 11m;

location / {
    proxy_pass http://127.0.0.1:3000;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_set_header X-Forwarded-For $remote_addr;
    proxy_read_timeout 60s;
}
```

`TRUST_PROXY=1` предполагает ровно один доверенный reverse proxy. Node должен быть закрыт от прямого внешнего доступа сетевым фильтром сервера. Не обслуживайте корень репозитория или каталог данных как static. Публичные файлы находятся только в `dist`.

## Подтверждение партнёров

Пользователь регистрируется в кабинете; затем координатор проверяет компанию. Административные команды выполняются из корня проекта с тем же `DATA_DIR`, что и основной сервер:

```sh
npm run admin -- users
npm run admin -- approve partner@company.ru
npm run admin -- revoke partner@company.ru
```

Отзыв доступа также удаляет сессии. Для сброса пароля задайте `NEW_PARTNER_PASSWORD` через закрытую конфигурацию окружения и выполните `npm run admin -- reset-password partner@company.ru`; затем удалите временную переменную. Пароль не передаётся аргументом командной строки. Не отправляйте пароли на email автоматически; согласуйте безопасную передачу с партнёром.

## Публикация предложений

Создайте локальный JSON с реальными данными, не помещая коммерчески чувствительную информацию в Git:

```json
{
  "title": "Название строительного проекта",
  "category": "Промышленное строительство",
  "region": "Регион проекта",
  "description": "Реальное описание состава работ, условий и требований к участнику.",
  "deadline": "2027-12-31",
  "contact": "coordinator@company.ru"
}
```

```sh
npm run admin -- add-tender /secure/path/tender.json
npm run admin -- close-tender 1
```

Истёкшие и закрытые предложения не выдаются API. Все подтверждённые партнёры видят общий пул предложений; индивидуальное распределение между компаниями в эту версию не входит. В пользовательском кабинете есть поиск, фильтр по направлению, раскрытие деталей и отклик через письмо координатору.

## Анкеты и доставка

```sh
npm run admin -- applications
npm run admin -- retry-mail
```

После подключения SMTP `retry-mail` проверяет подключение и пытается доставить ожидающие заявки. Фоновый worker проверяет очередь раз в минуту. При сбое повторные попытки используют растущую задержку до 24 часов. Статус `sent` означает, что SMTP принял письмо; попадание во входящие проверьте реальной согласованной отправкой. В тестах используется почтовый адаптер без внешней доставки.

Заявка содержит анкету во вложении, компанию, контакт, ИНН, комментарий и версию согласия. Получатель фиксирован: `antnpk@gmail.com`. `reply-to` — адрес заявителя. При отсутствии SMTP сайт сообщает, что анкета сохранена, а доставка ещё не настроена.

Удаление заявки и её закрытого вложения по запросу представителя:

```sh
npm run admin -- delete-application UUID
# Удаление аккаунта и его сессий (анкеты удаляются отдельно):
npm run admin -- delete-user partner@company.ru
```

Удаление из системы не удаляет уже отправленное письмо из почтового ящика: с ним администратор работает отдельно. Доступ к каталогу данных ограничьте учётной записью сервиса. Настройте резервное копирование SQLite штатным online backup или во время остановки сервиса вместе с вложениями; проверьте восстановление.

## Проверка запуска

Локально на сервере проверьте `/api/health` (ожидается `{"ok":true}`), HTML главной, загрузку исходного DOCX, регистрацию и блокировку `/api/tenders` до подтверждения. После настройки HTTPS проверьте cookie Secure и вход с обоих разрешённых хостов. После SMTP — одну реальную заявку и её статус/письмо во входящих. DNS, TLS и SMTP основного сайта компании не настраивались. GitHub Pages используется отдельно для тестирования интерфейса; серверные операции в этой сборке отключены.


## Тестовый интерфейс и полная серверная версия

GitHub Pages публикует `dist-pages` через workflow после успешных проверок ветки `sgt-design-preview`. Исходники разрабатываются в `main`; обновления для выпуска объединяются с `sgt-design-preview`. Эта ветка разрешена существующей политикой окружения `github-pages`; workflow соблюдает её без изменения ограничений. Это статическая версия с анимациями, навигацией, локальной проверкой формы и явно обозначенным демонстрационным кабинетом. Она не принимает заявки на сервер, не сохраняет аккаунты, не отправляет почту и не содержит реальных закрытых тендеров.

Полная серверная версия запускается через `npm run dev` или `npm start` в обычном окружении Node.js. Конфигурация `.devcontainer` подготовлена для GitHub Codespaces: Node.js 24, установка по lockfile, запуск на порту 3000. Сервер разрешает Origin конкретного Codespace по штатным переменным `CODESPACE_NAME` и `GITHUB_CODESPACES_PORT_FORWARDING_DOMAIN`, а не произвольные внешние хосты. При наличии `APP_ORIGIN` эта переменная имеет приоритет. Создание и проверка нового Codespace не выполнялись; локальные серверные и браузерные проверки выполнены в текущей среде.


При использовании другого домена задайте `CONSORTIUM_HOST=cons.ВАШ-ДОМЕН` и добавьте оба HTTPS-адреса в `APP_ORIGIN`. `HOST=127.0.0.1` ограничивает прямой запуск Node локальным интерфейсом за nginx; в Docker приложение слушает внутреннюю сеть `0.0.0.0` и не публикует порт 3000 наружу.
